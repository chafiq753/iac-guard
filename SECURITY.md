# Security Policy

iac-guard is a security tool and is often run in CI with access to source code and repository tokens. Vulnerabilities in it are taken seriously.

## Supported versions

| Version | Supported |
|---|---|
| 1.x (latest release) | Yes |
| < 1.0 (pre-releases, unreleased `main`) | No |

Security fixes are released as a new patch version. The `v1` tag of the GitHub Action and the `:1` / `:latest` Docker tags are moved to the fixed release.

## Reporting a vulnerability

**Do not open a public issue, discussion or pull request for a security problem.**

Report it privately by either of these methods:

1. **GitHub private vulnerability reporting (preferred):** go to the [Security tab](https://github.com/chafiq753/iac-guard/security) and click **Report a vulnerability**.
2. **Email:** cboulghallat@gmail.com, with the subject `[iac-guard security]`.

Please include:

- the affected component (CLI, Docker image, GitHub Action, dashboard) and version or commit;
- a description of the issue and its impact;
- steps to reproduce, or a proof of concept;
- any suggested fix, if you have one.

## What to expect

iac-guard is maintained by one person, so these are targets rather than guarantees:

| Step | Target |
|---|---|
| Acknowledgement of your report | within 3 working days |
| Initial assessment (confirmed or not, severity) | within 10 working days |
| Fix released for a confirmed high or critical issue | within 30 days |

You will be kept informed of progress. Once a fix is released, a GitHub Security Advisory is published and you are credited, unless you prefer to stay anonymous. Please allow time for a fix to be released before disclosing the issue publicly.

## Scope

**In scope**

- The `iacguard` Python package and CLI
- The Docker image `ghcr.io/chafiq753/iacguard`
- The GitHub Action (`action.yml`) and the workflow generated by `iacguard init --github`
- The optional dashboard (`backend/`, `frontend/`)

Examples of relevant issues include:

- command injection through action inputs or file names;
- a secret shown in clear text in a report, the terminal, annotations or SARIF;
- path traversal when reading or writing files;
- a way to make a scan **pass when it should block**, for example by bypassing `fail_on`, abusing `ignore` / `exclude`, or hiding findings;
- privilege escalation in the container;
- authentication, authorization or tenant isolation flaws in the dashboard.

**Out of scope**

- Vulnerabilities in **Gitleaks**, **Checkov** or **Semgrep** themselves: please report them to those projects directly.
- False positives or missed detections by a scanner rule. These are not security vulnerabilities: open a regular issue instead.
- Findings in the intentionally vulnerable demo files (`docs/demo-vulnerable-main.tf`, test samples).
- Issues that require an attacker to already control the repository's `.iacguard.yml` or workflow files.

## Security design

For reference, these measures are already in place:

- Gitleaks runs with `--redact`, so secrets never appear in clear text in the report. Code snippets that contain a secret are masked in every output.
- GitHub Action inputs are passed through environment variables, never interpolated into shell scripts.
- The scanners in the Action are installed in an isolated virtual environment.
- The Docker image runs as a non-root user (`uid 10001`). Read-only mounts (`:ro`) are recommended.
- Accepted risks require a written justification and can expire, so exceptions cannot be added silently or forever.
